# Reflect на своём сервере

Инструкция переносит Reflect с Replit на любой сервер с Docker. На сервере работают четыре контейнера:

| Контейнер | Что делает |
|---|---|
| `app` | Reflect: API и сайт в одном процессе |
| `db` | PostgreSQL 18, данные лежат в томе `pgdata` |
| `caddy` | HTTPS-сертификат (Let's Encrypt, выпускается сам) и проксирование на `app` |
| `backup` | каждую ночь в 03:00 по UTC (08:00 в Алматы) сохраняет базу в папку `backups/`, хранит 14 дней |

База наружу не открыта. Снаружи доступны только порты 80 и 443.

---

## 0. Попробовать без сервера

Чтобы посмотреть Reflect до установки, хватит компьютера с Docker или GitHub Codespace:

```sh
sh deploy/try-local.sh          # запустить; после обновления кода — то же самое
sh deploy/try-local.sh stop     # остановить, данные сохранятся
sh deploy/try-local.sh reset    # удалить тестовую базу и настройки
```

Скрипт сам создаст `.env` со случайными паролем и ключом и запустит базу и приложение на `http://localhost:8080`, без HTTPS и бэкапов. В Codespace адрес открывается на вкладке «Порты» (Ports), порт 8080. Для настоящей установки этот режим не подходит: используйте шаги ниже.

## 1. Что понадобится

- **Сервер.** Ubuntu 22.04 или 24.04, процессор **x86-64 (amd64)**, 2 vCPU, 4 ГБ памяти, 40 ГБ диска.
  - Серверы на ARM не подойдут: сборка рассчитана на x86-64.
- **Домен или поддомен**, например `app.reflect.kz`, с доступом к его DNS.
- **Доступ к серверу по SSH.**
- **Значение `ENCRYPTION_KEY` из Replit** (Secrets). Оно нужно, чтобы сохранённые токены Kaspi, МоегоСклада и MCP продолжили работать. Без него всё остальное перенесётся, но продавцам придётся ввести токены заново.

**Где взять сервер:**
- **В Казахстане:** PS Cloud, QazCloud, Kazteleport, VK Cloud (зона в Казахстане). Так данные продавцов хранятся в РК, а закон о персональных данных требует хранить данные граждан на территории страны. Как это относится к вашему случаю, уточните у юриста.
- **За рубежом:** Hetzner, DigitalOcean и другие. Обычно дешевле, но вопрос локализации данных остаётся открытым.

## 2. Направить домен на сервер

В DNS домена создайте **A-запись**: имя `app` (или `@` для корня), значение — IP сервера. Подождите 5–30 минут, пока запись разойдётся. Проверить можно командой `ping app.reflect.kz`: она должна показать IP вашего сервера.

## 3. Загрузить Reflect на сервер

С вашего компьютера:

```bash
scp Reflect-v0.14.zip root@IP_СЕРВЕРА:/opt/
ssh root@IP_СЕРВЕРА
apt-get update && apt-get install -y unzip
cd /opt && unzip Reflect-v0.14.zip -d reflect && cd reflect
```

Если код лежит в GitHub, вместо архива: `git clone https://github.com/…/Commerce-Intelligence-Platform.git /opt/reflect`.

## 4. Установить и запустить

```bash
cd /opt/reflect
./deploy/install.sh
```

Скрипт:
1. ставит Docker, если его нет;
2. спрашивает домен и `ENCRYPTION_KEY` (вставьте значение из Replit; если данные не переносите, нажмите Enter, и ключ сгенерируется);
3. создаёт `.env` со случайным паролем базы;
4. собирает образ (5–10 минут при первом запуске);
5. создаёт таблицы и запускает сервис.

Через минуту откройте `https://ваш-домен`. Для AI-ответов в «Спросить Reflect» добавьте в `.env` строку `ANTHROPIC_API_KEY=…` и выполните `docker compose up -d`.

**Закройте лишние порты:**

```bash
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw --force enable
```

## 5. Перенести данные с Replit

Это нужно, если в Replit уже есть продавцы и загруженные данные. Сначала остановите приём новых данных в Replit, чтобы ничего не потерялось между копированием и переключением.

**Вариант А: адрес базы Replit доступен снаружи.** Так бывает у production-базы опубликованного приложения: её адрес обычно содержит `neon.tech` или похожий хост, а не `helium`.

```bash
SOURCE_DATABASE_URL='postgresql://…?sslmode=require' ./deploy/migrate-from-replit.sh
```

**Вариант Б: база доступна только внутри Replit.** Так устроена база разработки, адрес вида `postgresql://…@helium/heliumdb`.

1. В Replit откройте **Shell** и выполните:
   ```bash
   pg_dump "$DATABASE_URL" -Fc --no-owner --no-acl -f reflect.dump
   ```
2. Скачайте `reflect.dump` из дерева файлов Replit и скопируйте на сервер: `scp reflect.dump root@IP_СЕРВЕРА:/opt/reflect/`.
3. На сервере:
   ```bash
   ./deploy/restore.sh reflect.dump
   ```

В обоих случаях скрипт заменяет текущую базу на сервере, потому что переносить нужно до начала работы на новом месте. Затем он обновляет схему и перезапускает приложение. Продавцы входят со своими прежними паролями.

> Если после переноса в настройках подключений написано «Ключ шифрования сервера изменился», значит `ENCRYPTION_KEY` в `.env` отличается от того, что был в Replit. Исправьте значение и выполните `docker compose up -d`.

## 6. Ежедневная работа

| Задача | Команда (из `/opt/reflect`) |
|---|---|
| Состояние сервисов | `docker compose ps` |
| Логи приложения | `docker compose logs -f app` |
| Перезапуск | `docker compose restart app` |
| Остановить всё | `docker compose down` (данные сохраняются) |
| Установить новую версию | заменить код (`unzip -o …` или `git pull`), затем `./deploy/update.sh` |
| Восстановить из копии | `./deploy/restore.sh backups/reflect-ГГГГ-ММ-ДД_ЧЧММ.dump` |

`update.sh` перед обновлением сохраняет копию базы в `backups/before-update-….dump`. Сервис будет недоступен около 10 секунд.

**Резервные копии лежат на том же диске**, что и база. Если сервер выйдет из строя, пропадут и они. Как вынести их наружу, описано в разделе 14: механизм уже встроен, остаётся выбрать хранилище и включить его. Проверить, что копия восстанавливается, можно командой `./deploy/verify-backup.sh`.

## 7. Если что-то не так

| Признак | Что проверить |
|---|---|
| Сайт не открывается, нет HTTPS | A-запись указывает на сервер; порты 80 и 443 открыты; `docker compose logs caddy` |
| `app` постоянно перезапускается | `docker compose logs app`. Если там сказано «ENCRYPTION_KEY must be set», заполните его в `.env` |
| Ошибка при `docker compose build`: Docker Hub недоступен | Укажите зеркало реестра в `/etc/docker/daemon.json` (`"registry-mirrors"`) или соберите с `--build-arg NODE_IMAGE=зеркало/node:22-bookworm-slim` |
| «Ключ шифрования сервера изменился» | `ENCRYPTION_KEY` не совпадает с прежним (см. раздел 5) |
| Продавец забыл пароль | `./deploy/reset-password.sh seller@example.kz` и отправить ссылку продавцу (раздел 13) |
| Продавец заблокирован: «Слишком много попыток» | После 3 неверных паролей на один email вход закрывается на 15 минут. Снять блок раньше: `./deploy/unlock-login.sh seller@example.kz` |
| Нужно сменить ключ шифрования | Старый ключ впишите в `ENCRYPTION_KEY_PREVIOUS`, новый — в `ENCRYPTION_KEY`, затем `docker compose up -d`. Токены перешифруются сами |

## 8. Без Docker (для опытных)

Нужны Node.js 22, pnpm 10 и PostgreSQL 16 или новее.

```bash
pnpm install --frozen-lockfile
PORT=5173 BASE_PATH=/ NODE_ENV=production pnpm --filter @workspace/shift-market run build
NODE_ENV=production pnpm --filter @workspace/api-server run build
DATABASE_URL=… pnpm --filter @workspace/db run migrate
NODE_ENV=production PORT=8080 STATIC_DIR=artifacts/shift-market/dist/public \
  DATABASE_URL=… ENCRYPTION_KEY=… node artifacts/api-server/dist/index.mjs
```

Запускайте процесс через systemd или pm2, а впереди поставьте Nginx или Caddy для HTTPS. Проверка готовности: `GET /api/readyz` отвечает `200`, когда работают и процесс, и база.

Replit-версия продолжает работать как раньше: файлы `.replit` и `artifact.toml` остались на месте.

## 9. Изменение схемы базы (для разработчиков)

Схема меняется только через версионные миграции, а не через `drizzle-kit push`: `push` сравнивает базу со схемой и может удалить колонку вместе с данными, а миграция — это SQL-файл, который можно прочитать до применения.

1. Измените таблицы в `lib/db/src/schema/`.
2. Выполните `pnpm --filter @workspace/db run generate`. Появится новый файл в `lib/db/migrations/`. Откройте его и проверьте: если в нём есть `DROP`, данные будут удалены.
3. Закоммитьте файл вместе с изменением схемы.
4. На сервере `./deploy/update.sh` сначала делает резервную копию, затем применяет только новые миграции (`docker compose run --rm migrate`).

Первая миграция (`0000_init.sql`) безопасна и для пустой базы, и для базы, где таблицы уже есть (например, восстановленной из Replit): существующие объекты она пропускает.

## 10. Удаление аккаунта и данных продавца

В приложении нет ни кнопки «Удалить аккаунт», ни «Удалить данные»: это сделано намеренно, чтобы сотрудник без полномочий не мог стереть данные компании со своего логина. Это делает администратор сервера:

```bash
./deploy/delete-account.sh seller@example.kz              # весь аккаунт
./deploy/delete-account.sh --data-only seller@example.kz  # только загруженные данные, аккаунт и подключения остаются
```

Скрипт показывает, что есть у аккаунта, просит ввести email ещё раз, делает резервную копию и только потом удаляет. Целый аккаунт уходит вместе со всем связанным, включая сохранённые токены Kaspi, МойСклад и MCP. Старые файлы в `backups/` остаются, пока не истечёт `BACKUP_KEEP_DAYS`: если человек просит полного стирания, удалите и их.

## 11. Автоматическая очистка

Раз в сутки (и через две минуты после запуска) сервер сам убирает то, что только растёт: просроченные сессии всех пользователей, записи журнала синхронизаций старше 90 дней, устаревшие счётчики лимитов. Синхронизации, застрявшие в статусе «выполняется» больше суток (сервер упал посреди работы), помечаются как прерванные. Если запущено несколько копий приложения, работу делает одна, остальные пропускают. Итог пишется в лог: `docker compose logs app | grep Maintenance`.

## 12. Ограничение входа

На один email разрешено 3 попытки входа за 15 минут, неважно, с каких адресов. Верный пароль обнуляет счёт. Адреса без аккаунта считаются так же, поэтому по ограничению нельзя узнать, кто зарегистрирован. Обратная сторона: посторонний может нарочно заблокировать чужой email на 15 минут. Для этого случая есть `./deploy/unlock-login.sh`.

## 13. Восстановление пароля

На странице входа есть «Забыли пароль?». Если в `.env` задан `SMTP_URL` (и при желании `MAIL_FROM`), продавцу приходит письмо со ссылкой. Ссылка ведёт на `https://DOMAIN` (или на `PUBLIC_URL`), работает один раз в течение часа, после смены пароля завершает все сессии и снимает блокировку входа.

Пока почта не настроена, ссылку создаёт администратор и отправляет продавцу сам (в мессенджер, по почте):

```sh
./deploy/reset-password.sh seller@example.kz
```

Форма «Забыли пароль?» отвечает одинаково для любого адреса, поэтому по ней нельзя узнать, у кого есть аккаунт.

## 14. Резервные копии вне сервера (когда появится хранилище)

Пока внешнего хранилища нет, копии лежат только на сервере. Механизм для переноса уже готов и выключен: контейнер `offsite` (rclone) копирует `backups/` во внешнее хранилище каждые 6 часов, а в самом хранилище держит копии 60 дней. Он работает только на копирование: удаление или порча файла на сервере в хранилище не отражается.

**Пока хранилища нет**, раз в неделю скачивайте папку на свой компьютер, например `scp -r root@IP_СЕРВЕРА:/opt/reflect/backups .`, и проверяйте свежую копию через `./deploy/verify-backup.sh`.

**Как включить, когда хранилище будет:**
1. Выберите хранилище: любое S3-совместимое (в том числе у казахстанских провайдеров), другой сервер по SFTP, Google Drive и прочее, что умеет rclone.
2. В `.env` раскомментируйте и заполните блок «offsite» (образцы для S3 и SFTP лежат в `.env.example`). `BACKUP_REMOTE` указывает, куда копировать: `offsite:имя-бакета/reflect`.
3. Запустите: `docker compose --profile offsite up -d offsite`. Лог: `docker compose logs offsite` (должна появиться строка `offsite: copied`).
4. Убедитесь, что файлы появились в хранилище, и один раз проверьте восстановление: скачайте файл оттуда и выполните `./deploy/verify-backup.sh файл.dump`.

**Шифрование.** В копиях лежат данные продавцов и зашифрованные токены. Если хранилище не вашего сервера, включайте шифрование на стороне rclone: добавьте в `.env` `RCLONE_CONFIG_OFFSITECRYPT_TYPE=crypt`, `RCLONE_CONFIG_OFFSITECRYPT_REMOTE=offsite:имя-бакета/reflect`, `RCLONE_CONFIG_OFFSITECRYPT_PASSWORD=…` (пароль задают в «обфусцированном» виде: `docker run --rm rclone/rclone obscure 'пароль'`) и поменяйте `BACKUP_REMOTE=offsitecrypt:`. Пароль шифрования храните отдельно от сервера: без него копии не прочитать.

**Регулярная проверка.** Раз в месяц запускайте `./deploy/verify-backup.sh`: он восстанавливает копию во временную базу рядом с рабочей, считает строки и удаляет временную базу. Рабочая база не затрагивается.
